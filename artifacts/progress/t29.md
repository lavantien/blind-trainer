## Report tail for the hub (2026-10-27, lane 15)

Divergences continued. LoadFontData in vendored rtext.c:614-760 stores a
glyph only when stbtt_FindGlyphIndex > 0, so codepoints missing from the
ttf are silently dropped and glyphCount < requested count is the only
signal. The port makes that fatal: bt_app_fonts_load will compare
requested count to font.glyphCount and scan glyphs[].value for every
requested codepoint. LoadFontEx keeps glyphs in request order, so
membership is a scan, not a binary search. TakeScreenshot in
rcore.c:1812-1833 resolves relative names against
CORE.Storage.basePath, which is the exe dir, not the cwd; the app passes
absolute shot paths. Screenshots read the post-EndDrawing swap
framebuffer via rlReadScreenPixels, matching the planned capture window
(shot taken after EndDrawing). No other surprises: window dims,
SetTargetFPS, input polling, and the png writer all behaved as
documented, probe exit 0 with a 1280x800 RGBA png at 47739 bytes.

Cross-lane fix 3a1d79c. Root cause: Rust std::fs::rename wraps
MoveFileEx with MOVEFILE_REPLACE_EXISTING, so renaming a legacy store
over an existing .migrated file succeeds. Plain C rename fails with
EEXIST on that case, so a legacy file reissued after the first import
broke the second load. Exposed only by the ported app persist test
legacy_stores_import_once_then_the_db_drives_loads, because no Rust data
test reissues a file after migration. Content: finish_renames delegates
to migrate_one, which tries rename, and on failure unlinks the target
first when stat says it is a regular file, then retries the rename;
directory targets keep failing so the existing blocker-test semantics
hold. New data test a_reissued_legacy_file_replaces_its_migrated_marker
pins it, data suite 33/33. Flagged here for the data lane because
src/data/import.c is theirs; minimal, test-covered, no API change.
