# t42 post-wave hoist of the duplicated whitespace predicate

## scope

Delete the core-local whitespace_len from src/core/alg.c and route bt_alg_parse through src/common/space.h bt_space_len, the shared predicate the ga lane landed. Config audit of config/constants_allow.txt rows for the hoisted literal. No behavior change, no opportunistic edits.

## findings

- Both implementations cover the identical codepoint set: ASCII 0x09 to 0x0D and 0x20 as 1 byte, U+0085 and U+00A0 as 2 bytes, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000 as 3 bytes. This equals the Rust bt-core text.split_whitespace() surface, which uses char::is_whitespace, the Unicode White_Space property. Probe points 0x0B, 0x85, 0xA0, 0x2028 plus every other class agree between the two C copies, so no new boundary pin is added. The existing alg.splits_unicode_whitespace test already pins 0x0B, 0x0C, 0x85, 0xA0, U+2028, U+3000 and stays unchanged.
- The unbounded core copy reads at most the NUL terminator, the shared copy is length guarded. With len = strlen(text) the two agree at every offset, including truncated lead bytes at end of string, both returning 0.
- config/constants_allow.txt row 12 (src/core/alg.c, literal 128, wide move marker byte) exists only because whitespace_len carried five 0x80 literals. Row 31 already covers src/common/space.c with literal 128. After the hoist the alg.c row is stale and is deleted, keeping policy honest without a duplicate.
- bt.py fmt has no per-file scoping, it is repo-wide. lint scopes per area: lint core covers src/core, src/common, and tests/unit/core. Formatting of touched files was checked by invoking the same clang-format binary with the same flags bt.py fmt uses, on the exact touched paths.
