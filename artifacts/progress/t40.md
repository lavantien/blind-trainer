# t40: lane L20 drivers port

Scope: crates/bt-app/src/{smoke,usage,usage_script}.rs to src/app/, the driver loop glue with OS key injection, bt.py screenshots target. Map rows t15-map 18, 21, 22.

Architecture decisions:
- The three Rust drivers are bevy plugins writing KeyboardInput messages and Screenshot requests. C ports split into a pure steppable model (smoke.c, usage.c: phase machines over bt_app_ctx with effect out-params, testable without a window, mirroring the Rust World-level tests) plus a thin raylib loop glue (drivers.c) that performs captures after frame end and injects keys.
- Key injection: views poll IsKeyPressed and GetCharPressed directly, so the usage tour's Press actions inject at the OS level via SendInput in a dedicated TU (driver_keys.c, windows.h only, never shares a TU with raylib.h). Nav and pin effects go through the existing production channels: bt_app_request_state, bt_app_nav_to_menu, bt_view_drill_set_pending, bt_view_case_drill_set_pending.
- Seeds: the drivers overwrite the published singleton seeds (bt_view_memo_app()->seed, bt_view_solve_app()->seed, bt_view_drill_app()->seed) before the states first consume them, mirroring insert_resource. Pulse frozen via bt_app_views_shared()->net.frozen.
- Rust constants (dwell, stuck limits, seed attempts, fatal reason) land as header defines per the port convention; no config changes needed (smoke_seed and cadence already exist).
- Open routing item for the hub: main.c currently parses the shot mode but never dispatches on it; the drivers land with their own entry points called directly by tests, and the report requests the 6-line main.c dispatch as the single frozen-surface change.
